# ADR-0015: GTFS-Realtime decoding, Google's protobuf runtime and generated classes

- **Status:** Accepted
- **Date:** 2026-10-16
- **Amended:** 2026-10-16, during E2.2: the proto is converted to proto3 before generation

## Context

- E2.2 decodes GTFS-Realtime, a Protocol Buffers format. PHP has no built-in protobuf support.
- Only the `gtfs-rt` driver may know the format (ADR-0001); the architecture test must name the namespaces to forbid elsewhere.
- About 400 TBM vehicles every 20 s: decoding speed matters little, one poll must stay under one second (E2.3).
- The schema is `gtfs-realtime.proto`, maintained in `google/transit` (last change 2026-08-17, `474750a`).

### PHP options on Packagist (2026-10-16)

| Package | Latest | State |
|---|---|---|
| `google/gtfs-realtime-bindings` (official) | 0.0.2, 2015 | Abandoned, PHP 5.3 era |
| `gtfs/realtime-php` | 1.0.0, 2019 | Abandoned, pinned to protobuf 3.10 |
| `dacoto/gtfs-rt-php` | 1.0.0, 2026-03 | One release, one maintainer, ~1,100 downloads |
| `gtfs-media/gtfs-realtime-php` | 1.1.0, 2026-08 | One maintainer, ~750 downloads |
| `google/protobuf` (runtime) | 5.36.2, 2026-09 | Maintained by Google, ~186 million downloads |

## Decision

1. **`google/protobuf`** is the only new dependency, in its pure-PHP form. The C extension is not installed: Ubuntu 26.04 does not package it, and the volume does not need it.
2. **The classes are generated by the project** from the official `gtfs-realtime.proto`, pinned to a commit of `google/transit`, with a `protoc` of the same release line as the runtime, run in Docker by one script (`scripts/generate-gtfs-realtime.sh`). `protoc` cannot generate PHP from proto2 `required` fields, so the script first converts the pristine upstream file to proto3: `required` becomes `optional` (presence is kept), custom defaults and extension ranges are dropped, and the three alert enums get a zero value. The wire format does not change; the generated classes decode a recorded TBM payload exactly like Google's Python bindings.
3. **Generated code is committed**, under its own directory with its own Composer autoload entry, outside `app/`: excluded from Pint, Larastan and CodeRabbit, and never edited by hand. Regenerating is one command; the diff shows any schema change.
4. **The architecture test forbids** `Google\Protobuf` and the generated namespaces outside `App\Ingestion`, and is proven once with a deliberate violation (E2.2).

## Alternatives considered

| Option | Why not |
|---|---|
| A third-party bindings package | Generated code like ours, but published by a single maintainer: a supply-chain risk for nothing we cannot generate |
| The C extension `protobuf` (PECL) | Faster, but not packaged by Ubuntu 26.04, so one more build step on the server and in the images, for a volume the pure-PHP runtime handles |
| Generating at install time instead of committing | Needs `protoc` on every machine and in CI; committing makes the code reviewable and the build simple |
| A hand-written protobuf decoder | Reimplements a binary format for no benefit |

## Consequences

- One runtime dependency, kept up to date by Dependabot; a major runtime upgrade regenerates the classes in the same pull request.
- The generated directory is large and machine-written; reviewers skip it, and the story file says so.
- Whether the pure-PHP runtime stays under the E2.3 budget is measured on a real TBM payload; the C extension is the fallback if it does not.
