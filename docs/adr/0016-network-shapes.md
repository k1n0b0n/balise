# ADR-0016: Line shapes as a GeoJSON file generated at import

- **Status:** Accepted
- **Date:** 2026-10-18
- **Amended:** 2026-10-24, story 026: the GeoJSON is kept in the network's import row, not in a file (point 3)

## Context

- The map should show every line of the network, faint, and the selected line more visible (E3.8, then E3.4). ADR-0002 keeps the database for the latest positions and leaves spatial queries to PostGIS, with the first spatial story.
- TBM static GTFS of 2026-10-17: `shapes.txt` is 19.6 MB, 514 shapes, 435,442 points, for 129 lines; shapes are tied to lines only through `trips.txt` (`route_id`, `shape_id`). Simplified at about 11 m, all 514 shapes weigh 132 KB compressed ([story 011](../stories/011-network-shapes.md#study)).
- The archive is rebuilt every night, and the daily import already skips an unchanged archive (`ETag`). Shapes themselves change rarely (service changes, works): a new archive does not mean new shapes.
- Nothing queries the shapes: they are drawn, never filtered by area or distance.

## Decision

1. **One GeoJSON file per network, generated by `network:import`**: one feature per line (its shapes merged, duplicates removed), simplified by the import, with the line id as property. Colours stay in the line catalogue: the file holds geometry only.
2. **Generated only when the shapes change**: the `gtfs` driver gives the shapes and their lines as app-owned values (ADR-0001), and the import compares a fingerprint of them (geometry and line of each shape) with the one of the last generation. A new archive with the same shapes writes nothing, so browsers keep their cached copy.
3. **A derived document, not a data store**: kept with its fingerprint in the network's import row (`catalog_imports.shapes`), rebuilt by the next import if lost, never edited. It was first a file under `storage/`; in production each container has its own `storage/`, so the import of the scheduler or of the deploy wrote where the `php` container never read, and a deploy lost it (story 026).
4. **Served like the line catalogue**: one endpoint per network, `no-cache` with the fingerprint as `ETag`, so a revisit gets a `304`; the map fetches it after the first positions, so vehicles never wait for it.
5. **One MapLibre layer, two states**: every line faint, in its colour; the selected line less transparent and wider (E3.4). The selected line meets WCAG 1.4.11 (3:1 against the basemap) with its transparency, measured in the story; the faint lines are decorative.

## Alternatives considered

| Option | Why not |
|---|---|
| Vector tiles (PostGIS `ST_AsMVT` or PMTiles) | Loads only the visible area and simplifies per zoom, but brings PostGIS or a tile build, for a network that fits in one small file; reconsidered when a second network makes the file too heavy (E6) |
| Shapes in PostgreSQL, one request per selected line | Only the selected line, but no whole-network view, and a request on every selection |
| Regenerating on every new archive | Simple, but a new `ETag` every night makes every browser download the same shapes again (RGESN) |
| Shapes inside the line catalogue | One request less, but the catalogue would grow tenfold and be fetched before the first draw |

## Consequences

- The import reads `trips.txt` (5.2 MB) as well as `shapes.txt` to tie shapes to lines; it stays a nightly job.
- The simplification tolerance and the real weight of the merged file are measured in E3.8 and recorded in its story; the per-line merge is expected to be two to three times smaller than 132 KB.
- A second network adds one file; vector tiles become worth an ADR when the files no longer fit one request comfortably.
