- **Status:** Done

## Acceptance criteria

## Notes

- **Image sizes** (uncompressed, arm64), first on `php:8.5-fpm-trixie` for every target: `runtime` 773 MB instead of 353 MB on Ubuntu, `dev` 837 MB, `test` 2.5 GB. The Debian image keeps its compilers (721 MB alone), and Playwright installed the full Chromium beside its headless shell (400 MB), Mesa and LLVM for a libgbm the shell only links (180 MB) and fonts for every script (87 MB). After moving `runtime` and `dev` to Alpine (ADR-0020 point 2 amended) and slimming `test`: `runtime` 176 MB (50 MB compressed), `dev` 194 MB, `test` 1.04 GB (268 MB compressed), `web` 102 MB.
- **`test` is flattened:** built in a `test-build` stage that purges the compilers, then copied into `FROM scratch`, so the base image's layers do not keep them; its `ENV` is declared again. Mesa goes with `dpkg --force-depends`, and the map's WebGL tests pass on the shell's SwiftShader.
- **busybox's `sha256sum` has no `--quiet`:** the GTFS-Realtime script checks protoc with `-c -` and discards the output; the protoc release runs on musl.
- **phpredis from GitHub, not PECL:** `pecl install` failed on a 504 from pecl.php.net during the first build; the release archive is fetched from GitHub and checked by SHA-256, then built with `docker-php-ext-install` like the bundled extensions.
- **`sockets` is needed:** Ubuntu's PHP had it built in; `pestphp/pest-plugin-browser` requires it, so the Dockerfile builds it.
- **nginx's official image compresses nothing** (`#gzip on;` in its `nginx.conf`): `site.conf` now turns gzip on itself.
- **CI in the image, measured:** 4 min 12 s from push to the final `ci` job, against 2 min 31 s for the single `setup-php` job on #57. Each job spends about a minute loading the 2.5 GB image from the cache and installing Composer packages; the image job takes 15 to 20 s once its cache is warm (4.5 min cold). Pint fails within about 80 s instead of after the whole run. Feature tests render pages, which need the Vite manifest, so they run after the front-end build, beside the browser tests.
- **Gotcha in GitHub expressions:** `cond && '' || 'x'` always gives `'x'`, since `''` is falsy; the run action tests `database != 'true'` instead.
- **Production images, measured:** `app` 246 MB (the runtime's 176 MB plus 55 MB of `vendor` without dev packages), `web` 104 MB. Smoke test against the local PostgreSQL: `/up` 200, the page and a hashed asset served by `web`, `optimize`'s caches built at start, the code read-only for `balise`. The build refuses to run without `POSTGRESQL_VERSION` and `REDIS_VERSION` as majors.
- **`web` copies `public/` from the `app` image of the same release** (`APP_IMAGE` build argument), so both serve the same built assets; the `dev` target of `docker/nginx/Dockerfile` never pulls it. A `.dockerignore` keeps `.env`, `vendor`, `node_modules` and local state out of every build context.
- **Bootstrap, measured on the three OrbStack machines:** first run `changed=16` (Debian), `15` (Ubuntu), `11` (shared); second run `changed=0` on all three. Docker 26.1 with Compose 2.26 on Debian, 29.1 with 2.40 on Ubuntu. On the shared machine, its Docker, its nginx, its other site and its other container were left as they were, and the firewall alone (`manage_firewall: false`). The site answers 502 until a first deploy starts the containers.
- **OrbStack machines are no longer isolated:** in an isolated machine, Debian 13's runc 1.1 fails with `BPF_PROG_ATTACH not supported` and no container starts; Ubuntu's runc 1.4 works there. A real Debian 13 kernel has no such limit.
- **Variable precedence:** the defaults live in `ansible/group_vars/all.yml`; the local machines' values in `ansible/inventory/group_vars/local.yml`, since group values written in an inventory file rank below a playbook's `group_vars/all`. A real inventory sets them per host, which ranks above.
- **Two env files and Compose's `.env`:** `app.env` (Laravel) and `postgres.env` (the database's password, the same one) are root-only and written by the bootstrap; Compose reads `.env` beside `compose.yaml` for interpolation, so that name is left to the versions written by the deploy.
- **Laravel trusts the proxy headers** (`trustProxies(at: '*')`): the host's nginx terminates HTTPS, so without them links and assets would be built with `http://`. PHP is only reachable through the web container. `tests/Feature/ProxyTest.php` fails without it.
- **`proxy_http_version 1.1`** in the host's site: nginx proxies with HTTP/1.0 by default, which the web container's `gzip_http_version 1.1` leaves uncompressed.
- **Deploy, measured on the three machines** through the restricted key, with three test releases pushed to a registry on the Mac (`registry:3` on port 5000, `host.orb.internal:5000` in the machines' `insecure-registries`): `v0.1.0` labelled PostgreSQL 17, `v0.2.0` labelled 18, `v0.3.0` without `public/index.php`. On each: `v0.1.0` imports 202 lines and 5,234 stops (about 20 s); `v0.2.0` moves PostgreSQL 17 to 18 by dump and restore, keeps the 5,234 stops and the ETag, so the import downloads nothing, and removes the old volume (about 25 s); `v0.3.0` fails the health check for 30 s and `v0.2.0` starts again; `rollback` goes back to `v0.1.0`, moving PostgreSQL 18 down to 17 the same way. Only the deployed versions' images stay. The shared machine's other site and container kept running.
- **The deploy key does nothing else:** `v0.1.0; id`, `id`, `$(id)`, two arguments and an empty command all get the usage line; a port forward is refused (`restrict`).
- **The deploy no longer renders the nginx site** (ADR-0020 point 7 amended): nothing in it depends on a release, and only the bootstrap writes host files. The health check now comes before the import, and a failed import leaves the release live.
- **`network:import` without an argument imports every network,** so the host's script names none.
- **The stopping queue worker and scheduler take about 10 s** (Laravel's graceful stop); the site keeps serving meanwhile, except during a PostgreSQL move.
- **Release workflow (`deploy.yml`), not run yet:** it runs on the first release after this story is merged. Checked so far: actionlint, the extraction of PostgreSQL's and Redis's majors from `compose.yaml`, and the `app` image built locally for `linux/amd64` (under emulation, 165 s for the extensions; PHP 8.5.11, the seven extensions, the generated classes, the labels). No build cache: a tag's run cannot read the caches of other refs, and nothing builds the production target on `main`.
- **The host's name and port are environment secrets, not variables:** a public repository's Actions logs are public, and only secrets are masked there.
- **GHCR packages start private:** the first published images must be made public by hand before the first deploy (`docs/deploy.md`).
- **Proof from scratch, in one go** (after merging E3.7 into the branch): the three machines deleted and created again, test releases rebuilt from the branch's head. Bootstrap `changed=17` (Debian), `16` (Ubuntu), `12` (shared), then `changed=0` on all three. Then, on the three machines at once: `v0.1.0` runs every migration, E3.7's included, and imports 202 lines and 5,234 stops in about 30 s; `v0.2.0` moves PostgreSQL 17 to 18 in about 27 s; `v0.3.0` goes back to `v0.2.0` after 30 s; `rollback` returns to `v0.1.0` and PostgreSQL 17 in about 18 s, with the 5,234 stops at every step and one volume left. On the shared machine the other site's file, Docker's `daemon.json` and the other container (same id, same start time) were untouched. The other site listens on IPv4 only, so check it on `127.0.0.1`, not `localhost`.
- **Ideas review:** no idea planned this story. *Next departures* stays Exploring, still waiting for the brief's scope and a trip updates port; the overview's argument for deploying first now reads "proven locally, not live yet" (E1.3e).
